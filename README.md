# zkevm-proof-of-ownership-kit

Self-service toolkit for stakeholders with funds locked in Smart Contracts on halted zkEVM mainnet — run a shadow-fork to simulate recovery, then prove ownership via message signatures.

## Background

Polygon zkEVM mainnet is halted. Some stakeholders have funds locked in Smart Contracts
on zkEVM mainnet that cannot be recovered through the standard exit-certificate tool,
because:

- The [exit-certificate tool](https://github.com/agglayer/aggkit/tree/develop/tools/exit_certificate) only covers EOA (externally-owned account) balances natively.
- Funds held by a Smart Contract are not included in the certificate — a contract's own
  fixed methods generally can't call a third-party `claimAsset`, and the contract itself
  may be immutable.

This toolkit exists to unblock exactly that case: **funds locked in a Smart Contract on
halted zkEVM mainnet.**

## What this kit does

It walks you through three steps:

1. **Spin up a shadow-fork** of zkEVM mainnet state, pinned to a known reference block.
2. **Impersonate** whatever addresses are needed (the Smart Contract, its owner(s),
   signers, etc.) on that fork to simulate the transactions that would move your locked
   funds to a destination EOA you control.
3. **Prove ownership** by signing a fixed message with the real key of every EOA that
   was impersonated in step 2 (or that controls an impersonated contract) — including
   the final destination EOA.

Step 3 is the critical gate. Impersonating an address on a local fork does **not** prove
you control it — anyone can impersonate any address on a fork they run themselves. The
message signature is the actual proof of ownership. Only after every required signature
is validated will Polygon generate an ad-hoc recovery certificate that lets you claim the
recovered funds on L1 through the normal claim UI.

**This kit only simulates and proves. It does not move real funds and does not generate
the recovery certificate.** The certificate is generated by Polygon after your submission
is reviewed and validated, using a separate internal tool.

## Who needs a signature

Every EOA impersonated during the shadow-fork simulation — the owner(s)/signer(s)
impersonated to authorize the fund movement — **and** the final destination EOA that
receives the recovered funds. If your case involves multiple owners or a multisig, every
impersonated signer needs to submit their own signature.

A contract has no private key and cannot sign. If the simulation impersonates a
contract directly, its ownership is proven by signatures from the EOA(s) that control it
on-chain (owner, multisig signers, admin), together with an explanation of that control
path in your submission.

## Message format

Ownership is proven with a **plain fixed message**, signed via standard `personal_sign`
(EIP-191), one signature per address:

```text
I confirm ownership of <address> for zkEVM fund recovery — nonce: <nonce> — date: <date>
```

Use `ownership-proof/sign-message.sh` to produce each signature — do not sign an ad-hoc
message on your own, as it will not match what Polygon's verification step expects. It
signs through `cast` with a hardware wallet (`--ledger` / `--trezor`), a Foundry keystore
(`--account`), or a hidden key prompt (`--interactive`); raw private keys on the command
line are refused.

No terminal, or a cold wallet only usable from the browser? Print the exact message with
`sign-message.sh --print-message` and sign it at
[etherscan.io/verifiedSignatures](https://etherscan.io/verifiedSignatures) instead — see
[`cases/_template/README.md`](cases/_template/README.md).

## Prerequisites

- [Docker](https://docs.docker.com/get-docker/), running — the shadow-fork (`anvil`) runs
  from the official Foundry image, so Anvil itself needs no install.
- The [Foundry toolchain](https://getfoundry.sh) — provides `cast` (impersonation, sending
  transactions, and signing messages). Everything in this kit is plain bash built on top
  of `cast`; no Node/Go toolchain required.
- `curl` and `jq`.

`setup/fork.sh` checks at start that `docker` (and its daemon), `curl` and `jq` are
available and tells you what is missing; it only warns if `cast` is not installed.

## How to use this kit

1. **Fork.** Follow `setup/` (see below) to spin up and verify your shadow-fork.
2. **Start your case.** Run `cases/new-case.sh <your-case-id>` (it copies
   [`cases/_template/`](cases/_template/README.md) to `cases/<your-case-id>/`) and follow
   its README — it walks you through declaring what you recover in `recovery.json`,
   filling in `move.sh`, running it against the fork, and collecting signatures into
   `signatures.json` for every impersonated address plus your destination EOA.
3. **Package and submit.** Run `submission/prepare-submission.sh cases/<your-case-id>` (it starts a fresh fork and stops it afterwards; `--no-fork` uses one you already have running):
   it runs your `move.sh`, checks the result against `recovery.json` and that
   `signatures.json` (filled in beforehand) holds a valid signature for every impersonated
   EOA plus the destination — if one is missing it stops and prints the command to sign
   it — and writes a single `.tgz`, telling you at the end where to send it and how to
   verify it. Email that file to
   [`zkevm-claims@polygon.technology`](mailto:zkevm-claims@polygon.technology) for review
   (see [`submission/SUBMIT.md`](submission/SUBMIT.md)).

### Running the shadow-fork

```bash
cd setup
cp .env.example .env   # optional, defaults work out of the box
source .env
./fork.sh
```

`fork.sh` pins the fork to the network's halt block and refuses to start if that block
doesn't match the RPC's current latest block — so a stale or wrong RPC endpoint fails
loudly instead of silently forking the wrong state. Leave it running in its own terminal;
it's the node the rest of the kit connects to.

Everything it prints (including Anvil's own output) is also saved to `setup/fork.log`
(override with `FORK_LOG`), overwritten on every start — you submit that file, so don't
copy the console by hand. If your RPC URL carries an API key it is masked in both places.
